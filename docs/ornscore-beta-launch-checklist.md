## (c) §10 종목 커버리지 확대 단계 + 제한 안내

현재 **분석 대상 138종목**(전체 상장 종목 아님). 처음부터 전체를 넣으면 데이터 품질 관리가 어려우므로 단계적으로 확대한다. 소유자 **[개발]**, 전체 **대기④**(데이터 품질·파이프라인 동반).

| 단계 | 범위(§10.1~10.3) | 상태 | 비고 |
|---|---|---|---|
| 현재 | 138종목(테마/시총 기준 선별) | 완료 | `/status`·`knownLimits` "종목 커버리지"로 노출 |
| 1단계 | KOSPI200 · KOSDAQ150 · 주요 ETF | 대기④ | 우선 확대 대상. ETF는 점수 산식 적용 가능성 별도 검토 |
| 2단계 | 시총 상위 500 · 거래대금 상위 500 · 주요 테마 | 대기④ | 재무 수집 커버리지 확인 필요 |
| 3단계 | 전체 KOSPI/KOSDAQ · ETF/리츠 분류 · 우선주/스팩/관리종목 제외 옵션 | 대기④ | 가장 큰 작업. 필터 옵션 동반 |

### §10.4 커버리지 확대 시 주의사항(확대 전 반드시 동반할 표시)

확대할 때 아래 표시 규칙을 함께 넣어야 품질 저하가 사용자 신뢰를 깨지 않는다.

- 데이터 품질이 낮은 종목은 **별도 표시**(현재 `isSuspect` 검증 보류 패턴 재사용 가능)
- 거래량 부족 종목은 **경고 표시**
- 관리종목/거래정지 종목은 **기본 필터에서 제외**
- 신규상장주는 **점수 산출 제한**(가격 이력 부족)
- 재무 데이터가 부족한 종목은 **점수 신뢰도 낮음 표시**(현재 `missingFinancials` 결측 표시 패턴 재사용 가능)

### 사용자용 제한 안내 문구안(확대 전/중 노출)

이미 `/status` "알려진 제한"에 다음 1줄을 추가했다(이번 Task 47, `dataStatus.knownLimits`):

> **종목 커버리지** — 현재 분석 대상은 138종목이며, 전체 상장 종목이 아닙니다. KOSPI200·KOSDAQ150·주요 ETF부터 단계적으로 확대할 예정이며, 데이터 품질 검증이 끝난 종목만 순차 추가합니다.

확대 시작 시점에 덧붙일 후보 문구(아직 미적용, 라이브 시 검토):

> 새로 추가된 종목은 데이터 축적 기간이 짧아 점수 신뢰도가 낮을 수 있습니다. 검증 보류 종목은 오늘 후보·Top 목록에서 제외됩니다.

## (d) §14 관리자 기능 — MVP(얇게) vs 후속

설계서 §14의 관리자 페이지를 한 번에 다 만들 필요는 없다. **읽기 전용 현황판(MVP)**과 **쓰기/운영 작업(후속)**으로 나눈다.
현재 가장 가까운 표면은 사용자용 `/status`(selfCheck: 검증 보류·결측·산식 일치). 관리자 전용 화면은 미구현.

| §14 영역 | 관리자 MVP(얇게, 읽기 전용) | 후속(쓰기·운영) |
|---|---|---|
| 14.1 대시보드 | 오늘 수집/점수 계산/공시 수집 현황 **표시**(현재 `/status` selfCheck가 근접) · 오류 신고 건수 | 결제 사용자 수·활성 사용자·알림 발송 성공률·서버 상태(라이브 인프라 필요) |
| 14.2 데이터 관리 | 종목별 데이터 **확인**(읽기) · 수집 로그 확인 | 데이터 재수집·점수 재계산·공시 재분류·제외 처리·상태 변경(쓰기 트리거 → 파이프라인 §15.1) |
| 14.3 사용자 관리 | 회원 목록·구독 상태 **조회** | 결제 이력·계정 정지/해제·신고 처리(결제·권한 시스템 §15.3·§15.4) |
| 14.4 콘텐츠 관리 | 현재 고지/카피는 코드 단일 소스(`dataStatus`·`pricing`)에서 관리 | 지표 가이드·공시 설명·FAQ 화면 편집 UI(후순위) |

- MVP 소유자 **[개발]**, 후속 소유자 **[개발]/[제품]**. 전 항목 **대기④**(관리자 인증·영속 저장·쓰기 트리거 신규 시스템).
